# 13. Internationalization: react-i18next, set up before adding more copy

## Status

Accepted

## Context

The client app (`web/src/app/` + the shared landing page) is about to get more pages — starting with a proper Home page explaining the project — which means writing more English copy. Retrofitting translation into a page full of hardcoded strings later means hunting down every string by hand; doing it before that copy lands is cheap by comparison.

## Decision

**`react-i18next`**, not a hand-rolled context, for the client app (`web/src/App.tsx`, `web/src/app/`, and the shared `web/src/ui/` components they use). It's the de facto standard for React, handles interpolation (`{{name}}`) and the `<Trans>` component for text with embedded markup (e.g. "Logged in as **email**") for free — a custom solution would need to reinvent both as soon as either came up, which `scan.readCount` ("Read 2 of 3 photos") already needed on day one.

Two languages to start: English (`web/src/locales/en.json`) and Spanish (`es.json`), one flat JSON file per language — no namespace-splitting, the app is small enough that one file per language stays easy to scan.

Language is detected from the browser (`i18next-browser-languagedetector`, `navigator.language`) and overridable via a manual toggle (`ui/LanguageToggle.tsx`) in the nav and on the auth/landing pages, persisted to `localStorage` so a manual choice sticks across visits.

**Scope: the client app only, not the admin UI** (`web/src/admin/`). Admin is an internal tool for managing the allergen catalog, not something a non-English-speaking end user ever touches — translating it would be effort spent on an audience that doesn't exist.

## Consequences

- Every new client-app page or component from here on writes translation keys, not hardcoded strings, in both `en.json` and `es.json` — a key added to one and not the other falls back to English via `fallbackLng`, so it fails soft (a missing translation shows English, not a broken key like `scan.title`) rather than hard.
- Tests assert against English copy; `setupTests.ts` pins `i18n.changeLanguage('en')` so a stray `localStorage` value or jsdom's `navigator.language` can't make a test non-deterministic.
- A server-side error message (e.g. a Rails validation error surfaced via `SignUpPage`'s `err.message`) is still English-only — translating API error text is a separate, larger effort (the backend would need to speak multiple languages, not just the frontend) not undertaken here.
- No pluralization rules needed yet (`scan.readCount` sidesteps it with "photo(s)") — `react-i18next`'s plural support is there if a more natural phrasing is wanted later.
